# AegisDB

A relational engine you can read in an afternoon and measure against SQLite in a minute.

**SQL in → cost-based plan out → Volcano execution**, with a textbook storage manager, ARIES recovery, and snapshot isolation. The point of the repo is not to beat SQLite. It is to implement the real machinery, then publish the numbers that show *where* a clean engine loses and *why*.

```
SQL  →  lexer/parser  →  logical plan  →  Selinger DP optimizer
     →  physical plan  →  Volcano iterators  →  tuples
                              │
              slotted pages ← buffer pool (clock + LRU) ← disk
                              │
                    WAL (steal/no-force)  +  MVCC version chains
```

```bash
make            # aegisql, aegis_test, bench_tpch
make test
make bench      # TPC-H subset vs SQLite; writes docs/BENCHMARKS.md
./aegisql mydb
```

```sql
CREATE TABLE lineitem (
  l_orderkey INTEGER,
  l_quantity INTEGER,
  l_extendedprice DOUBLE,
  l_discount DOUBLE,

EXPLAIN SELECT SUM(l_extendedprice * l_discount) FROM lineitem
        WHERE l_shipdate >= '1994-01-01' AND l_quantity < 24;
```

## What is implemented

| Layer | Pieces |
|---|---|
| **Storage** | 4 KiB slotted pages, length-prefixed tuple serialization with xmin/xmax version chains, clock (second-chance) buffer pool with LRU fallback, heap files, page-level free-space map |
| **Indexing** | B+ tree (split, merge/borrow, sibling range scan), extendible hash (directory doubling + overflow chains), Bloom filters in front of both |
| **Planner** | Recursive-descent SQL → logical plan → **Selinger-style left-deep DP join order** with NDV/min/max cardinality estimates → physical plan |
| **Executor** | Volcano `Init/Next/Close`: sequential scan, index scan, hash join, sort-merge join, nested-loop join, hash aggregate, external merge sort, limit |
| **Transactions** | ARIES WAL (LSN-tagged records, steal/no-force), analysis/redo/undo with CLRs, dirty-page table + transaction table, **MVCC snapshot isolation**, strict 2PL lock table (wait-die) |

SQL subset: `CREATE TABLE/INDEX`, `INSERT`, `SELECT` (joins, `WHERE`, `GROUP BY`, aggregates, `ORDER BY`, `LIMIT`), `EXPLAIN`, `ANALYZE`, `BEGIN/COMMIT/ROLLBACK`. Indexes: `CREATE INDEX ... USING HASH` for extendible hashing.

## Layout

```
include/aegisdb/
  storage/     page, disk, buffer pool, slotted page, heap, FSM, tuples
  index/       B+ tree, extendible hash, Bloom filter
  parse/       lexer + recursive descent
  plan/        Selinger optimizer + physical operators
  exec/        Volcano iterators
  txn/         MVCC snapshots + 2PL lock table
  recovery/    log records, log manager, ARIES restart
  engine.hpp   Database: SQL in, QueryResult out
```

## Why the SQLite comparison exists

A storage-engine resume project that never races a production baseline is a collection of data structures. The benchmark is a TPC-H-shaped subset (Q1, Q6, Q3) plus crash-reopen time. SQLite wins; the write-up in `docs/BENCHMARKS.md` says exactly which layer paid for it (heap vs clustered B-tree, userspace clock pool vs kernel pager, Volcano vs VDBE, ARIES vs WAL frames).

## Reusing Bloom filters

`BloomFilter::Clear()` removes inserted entries while retaining the allocated capacity and hash count. Reuse the filter with `Add()` afterward. An uninitialized filter remains conservative and returns `true` for possible membership.

`Reset()` validates requested capacity before allocating; an overflowing request raises `std::length_error` and preserves the previous filter. `make test` includes clear/reuse and capacity-overflow regression checks.
